# 테넌트 1000개로 늘어나면 캐시를 어떻게 둬야 하나 (쉽게 정리)

> 대상: %클라우드(Tomes-Cloud), 브랜치 feat-code-cache
> 작성: 2026-06-23 (검증 완료본)
> 질문: "지금 Redis 캐시는 고객사(테넌트)가 1000개일 때를 생각 안 하고 만든 건데,
>        고객사가 늘면 캐시를 'GC가 관리하는 메모리'에 두는 게 낫지 않을까?"

---

## 한 장 요약

- 지금 캐시는 **Redis라는 별도 창고**에 들어 있다. 앱 서버 메모리(힙) 바깥이다.
- "GC를 도입하자"는 말은 사실 **"캐시를 앱 서버 메모리 안으로 옮기자"**는 뜻이다.
- 결론: **옮기면 안 된다.** 고객사 1000개에선 오히려 더 느려지고 불안정해진다.
- 진짜 고쳐야 할 건 GC가 아니라 **(1) 무효화 방식 (2) Redis 용량 정책 (3) 캐시 키 개수**다.

---

## 1. 용어부터 — "GC를 둔다"가 무슨 뜻인가

쉽게 비유하면:

- **Redis 캐시 (지금 방식)**
  = 회사 건물에 **공용 창고**가 하나 있고, 모든 앱 서버가 그 창고를 같이 쓴다.
  창고는 앱 서버 바깥에 있다(별도 프로그램).

- **온힙 캐시 (= "GC 도입" 안)**
  = 캐시를 창고가 아니라 **각 앱 서버의 책상 서랍 안**에 둔다.
  서랍이 꽉 차면 자동으로 오래된 걸 버리는데, 그 청소부가 바로 **GC**다.

즉 "GC를 도입하자"는 **"공용 창고 대신 각자 책상 서랍에 캐시를 넣자"**는 말이다.
GC는 따로 켜는 기능이 아니라, 캐시를 앱 서버 메모리 안에 둘 때 자동으로 따라오는 청소부다.

---

## 2. 지금 캐시가 어떻게 생겼나 (사실 확인 결과)

- 서버 캐시는 **전부 Redis(공용 창고)** 에 있다.
  앱 서버 메모리 안에 두는 캐시 라이브러리(Caffeine 등)는 **하나도 안 쓴다.**
- 로그인 세션도 Redis에 둔다 → 앱 서버 메모리가 세션 때문에 부풀지 않는다.
- 캐시 종류와 "구분 기준(키)":

  - 고객사별로 1개씩 만들어지는 것 (가벼움):
    사용자 목록, 설비 목록, 담당자 목록.
  - 고객사 × 추가조건으로 늘어나는 것 (주의):
    공통코드 목록, 거래처/외주처 목록, 창고위치 목록.
  - 전체가 1개만 있는 것 (아주 가벼움): 시스템 목록.
  - 고객사와 무관하게 파일 개수만큼 늘어나는 것: 이미지 정보.

- 캐시 유지 시간(TTL)은 지금 쓰는 게 **전부 1시간**이다.
- 참고: 거래처 전체목록(selectCompList)과 가격코드(getChargeList)는
  **사실상 캐시가 안 걸려 있다**(매번 DB 조회).

## 3. 고객사 1000개가 되면 진짜 문제가 되는 곳 (GC와 무관)

### 문제 1 (제일 심각) — 한 고객사가 저장하면 1000개 고객사 캐시가 다 날아간다

지금은 캐시를 지울 때 **그 종류 전체를 통째로 비운다.**
예를 들어 A 고객사가 거래처 하나를 저장하면, **B~Z 1000개 고객사의 거래처 캐시까지
전부 같이 지워진다.**

- 고객사 1개일 땐 아무 문제 없다.
- 고객사 1000개면 **누군가는 늘 뭔가를 저장하고 있다** → 캐시가 계속 비워진다 →
  캐시가 있으나 마나 한 상태가 되고, 그 부담이 전부 DB로 간다.

이건 캐시를 창고에 두든 서랍에 두든 **똑같이 생기는 문제**다. GC로는 안 풀린다.

### 문제 2 — Redis 창고에 "용량 한도"와 "꽉 차면 어떻게 할지"가 안 정해져 있다

설정 파일엔 Redis 주소만 적혀 있고, **최대 용량/정리 규칙이 코드에 없다.**
이건 NCP(클라우드) Redis 서버 설정에 맡겨져 있다.
만약 그 설정이 "꽉 차면 그냥 거부"로 돼 있으면, 용량이 차는 순간 캐시 저장이 실패할 수 있다.
→ **NCP Redis 설정값부터 확인해야 한다.**

### 문제 3 — 일부 캐시는 고객사 수보다 더 빨리 늘어난다

대부분은 "고객사당 1개"라 1000개여도 가볍다.
다만 공통코드/거래처처럼 **고객사 × 추가조건**으로 늘어나는 건 개수가 더 빨리 분다.
Redis(용량 큰 창고)엔 견딜 만하지만, 만약 앱 서버 서랍에 넣으면 감당이 안 된다(아래).

## 4. 방법별 장단점 (고객사 1000개 기준)

### A. 지금 방식 — Redis 공용 창고
- 좋은 점: 앱 서버 여러 대가 **창고 하나를 같이** 본다 → 캐시가 잘 맞고 중복이 없다.
  앱 서버 메모리와 분리돼 있어 **GC(청소) 부담이 거의 없다.**
- 아쉬운 점: 캐시 꺼낼 때 창고까지 다녀오는 시간(네트워크)이 약간 든다.
  + 위의 문제 1, 2가 남아 있다.

### B. "GC 도입" = 앱 서버 서랍에 캐시 두기
- 좋은 점: 서랍이 바로 옆이라 **꺼내는 게 아주 빠르다.** 서랍 용량 한도도 쉽게 건다.
- **나쁜 점 (1000개에선 치명적)**:
  1. 캐시 수백 MB가 앱 서버 메모리에 쌓이면 → **청소(GC)할 때 앱이 잠깐씩 멈춘다.**
     메모리 걱정을 덜려던 게 오히려 멈춤을 만든다.
  2. 앱 서버가 여러 대면 **각 서랍에 같은 걸 중복 보관** → 메모리 낭비 + 캐시 덜 맞음.
  3. A 서버 서랍을 비워도 **B 서버 서랍은 안 비워진다** → 서버마다 다른 옛 데이터를 본다.
     맞추려면 복잡한 동기화 장치를 새로 만들어야 한다.

### C. 절충 — 자주 쓰는 것만 서랍에, 나머지는 창고에 (2단 캐시)
- 좋은 점: **전 고객사 공통인 아주 인기 캐시(예: 시스템 목록)** 만 서랍에 작게 두면
  창고 왕복을 줄일 수 있다.
- 아쉬운 점: 서랍/창고 동기화가 필요하고, 서랍을 작게 유지해야 한다.
  크게 잡으면 B의 단점이 다시 생긴다.

### D. 지금 Redis 유지 + 약점만 보강 (추천)
1. **무효화를 콕 집어서** — 전체를 비우지 말고 **그 고객사 것만** 지운다. (문제 1 해결)
2. **Redis에 용량 한도 + "꽉 차면 오래된 것부터 버리기" 규칙 설정** (문제 2 해결).
   이게 사용자가 원했던 "메모리 자동 관리"의 진짜 답이다 — GC가 아니라 Redis 설정이다.
3. 너무 잘게 쪼개지는 캐시 키를 줄여 개수를 정리 (문제 3 해결).

## 5. 결론

**캐시는 Redis(공용 창고)에 그대로 두는 게 맞다.**
캐시를 앱 서버 서랍(온힙/GC)으로 옮기는 건 고객사 1000개에선 오히려 손해다 —
앱이 멈추고(GC), 서버마다 중복되고, 데이터가 서버마다 달라진다.

해야 할 일 (순서대로):
1. **무효화를 "그 고객사 것만" 지우게 바꾸기** — 가장 급함, 캐시 효과에 직결.
2. **NCP Redis에 용량 한도 + 자동 정리 규칙 켜기** — "자동 관리"의 정답.
3. 캐시 키 개수 정리.
4. (선택) 전 고객사 공통 인기 캐시만 작은 서랍 캐시 추가(2단).

**한 문장**: 고객사 1000개 문제는 "GC(서랍 캐시) 도입"이 아니라
"무효화 정밀화 + Redis 용량/정리 규칙 + 키 개수 정리"로 푼다.
서랍 캐시는 오히려 멈춤·중복·불일치를 부른다.

- 무효화 전체비움: 거래처/설비/사용자 저장 = `@CacheEvict(allEntries=true)`,
  코드/범용저장 = `Cache.clear()`. 둘 다 종류 전체를 비움.
- Redis 설정: develop/production yml에 host만 있음. 용량/정리정책은 NCP 서버 몫.
