# %테스트 현대화

## 현재 상태

- 상태: 코드·실동작 검증 완료 / Google Workspace OAuth 사용자 인증 대기
- 작업일: 2026-08-10
- 대상: `Projects/Test-Automize`
- 브랜치: `claude`

## 현상

- 기준 전체 테스트는 OSR-173 계획이 `assert_eval`에서 원자 레시피로 바뀐 뒤
  테스트 코드가 따라가지 못해 191 PASS / 3 FAIL이었다.
- 누적 실행기는 과거의 30건 배치·자동 Stage4 heal 정책을 남겨 현재의
  결정론 우선·최대 20건·Stage4 명시 허용 정책과 충돌했다.
- AI 보조 도구의 모델·프로필·직접 CLI 호출과 제품/테스트 저장소 절대경로가
  여러 파일에 분산돼 있었다.
- `--skip-global-seeds`가 사용자 golden seed를 막지 못했다.
- GWS CLI가 없어 최신 Sheet 대신 2026-05 로컬 캐시를 사용했다.

## 해결

- `claude_runtime.py`로 선택적 AI 모델·config·SDK/Stage4 CLI 설정을 통합했다.
  일반 QA와 누적 회귀는 AI를 호출하지 않으며 Stage4는 계속 opt-in이다.
- Stage4는 지정 QA MCP만 로드하고 기본 도구·추가 MCP·세션 저장을 끈다.
- `cumulative_run.py`의 자동 heal을 제거하고 batch를 1~20으로 제한했다.
- 활성 코드의 과거 `D:\Personal`, `Tuning_Automize`, 구형 제품 경로를 저장소
  상대경로와 `.env`의 `TOMES_ROOT` 기준으로 교체했다.
- OSR-173은 현재 제품 `body-script.jsp`의 코드별 W/H/T/D/L 표시 계약과 실제
  옵션을 검증한다. 없는 `S05R70`을 만들지 않고 `disabled`를 oracle로 쓰지 않는다.
- `--skip-global-seeds`가 사용자 seed까지 포함해 모든 runner-wide seed를 생략한다.
- GWS CLI 0.22.5를 `D:\Tool\nodejs`에 설치하고 config를 `D:\ToolData\gws`로
  고정했으며 Python에서 현재 npm의 `bin\gws.exe`를 찾도록 수정했다.

## 남은 작업

- GWS OAuth client와 사용자 로그인이 없다. Workspace OAuth desktop client를
  `D:\ToolData\gws\client_secret.json`에 두거나 다른 인증 방식을 선택한 뒤
  `gws auth login`이 필요하다.
- 인증 전에는 `logs/sheet_cache.json` fallback만 사용한다. 캐시 row 899의
  `menu2=외주주문관리`와 `screen_name=외주발송이력` 불일치는 최신 Sheet를
  읽은 후에만 정정한다.
- 외부 AI 호출은 과금·업무 데이터 전송을 피하기 위해 이번 검증에서 실행하지 않았다.
