# 견적 단가검토 추가금액 테이블 구성안

- 작성일: 2026-07-13
- 대상: 상세 견적검토의 배송비·기타추가·수량 적용가·적용 금액계
- 목적: DB 변경 승인 전에 가능한 데이터 모델을 비교하고 권장안을 제시
- 범위: 분석 문서만 작성. DDL·애플리케이션 코드는 변경하지 않음
- 보관: 2026-07-29 `%클라우드`의 미추적 산출물에서 `&하네스/logs` 분석 기록으로 이동

## 1. 요구사항 정리

다음 기호를 사용한다.

- `B`(기존 총합): 배송비와 신규 기타추가를 제외한 기존 단가 구성요소 합
- `Q`: 수량
- `D`: 배송비
- `A`: 신규 기타추가
- `M`: 사용자가 수정할 수 있는 적용 금액계

요청된 화면 계산식은 다음과 같다.

| 화면 항목 | 계산식 | 수정 가능 여부 |
|---|---:|---|
| 단가합계 | `B + D + A` | 파생값 |
| 금액계 | `B × Q + D + A` | 파생값 |
| 수량 적용가 | `B × Q` | 파생값 |
| 적용 금액계 | 기본값 `B × Q + D + A` | 사용자 수정 가능 |

배송비와 신규 기타추가는 수량에 비례하는 단가가 아니라 상세 행에 마지막으로 한 번 더하는 가산액이다. 따라서 이름에 `UNIT_`을 붙여 단가 구성요소처럼 취급하면 계산 오류 가능성이 커진다.

## 2. 현재 구조에서 확인된 사실

### 2.1 기존 기타비용은 이미 별도 의미를 가진다

`TBL_ESTIMATE_DETAIL.UNIT_ETC_AMT`는 현재 다음 항목들과 함께 기존 단가 `B`를 구성한다.

- 소재비·소둔·제관
- 용접·가공·연마
- 표면처리·열처리
- 기존 기타비용 `UNIT_ETC_AMT`

현재 여러 쿼리는 아래 형태로 계산한다.

```text
B = 소재비 + 소둔 + 제관 + 용접 + 가공 + 연마 + 표면처리 + 열처리 + UNIT_ETC_AMT
기존 금액계 = B × Q
```

저장소 기준 `UNIT_ETC_AMT`는 29개 파일에서 216회 참조된다. 견적 조회·등록·수정뿐 아니라 엑셀, Jasper 리포트, 유사형상, 수주 변환 및 작업지시 단가에도 전파된다.

따라서 `UNIT_ETC_AMT`를 신규 기타추가 `A`로 재정의하면 과거 데이터와 모든 기존 계산식의 의미가 함께 바뀐다. 이 방식은 피해야 한다.

### 2.2 배송비는 화면 식별자만 있고 SQL 영속화가 없다

`DELIVERY_AMT`는 견적등록·견적목록·수주관리 JavaScript 컬럼명으로 등장하지만, 저장소의 SQL 매퍼에는 조회·INSERT·UPDATE 연결이 없다. 상세 견적검토 JSP에는 `UNIT_DELIVERY_AMT` 입력이 임시로 존재하나 DB 응답에 없고 저장 쿼리에서도 무시된다.

즉 현재 화면에 이름이 있다는 사실만으로 실제 DB 컬럼이 존재하거나 값이 보존된다고 판단할 수 없다.

### 2.3 적용 금액계를 저장할 기존 전용 컬럼이 없다

현재 `UNIT_FINAL_EST_AMT`는 최종 견적 **단가**다. 여러 화면과 쿼리가 `UNIT_FINAL_EST_AMT × 수량`을 금액계로 사용한다. 사용자가 수정하는 신규 적용 금액계는 **총액**이므로 `UNIT_FINAL_EST_AMT`에 저장할 수 없다.

### 2.4 견적에서 수주로 값이 복사된다

견적에서 주문을 만들 때 다음 흐름이 존재한다.

```text
TBL_ESTIMATE_DETAIL
  ├─> TBL_ORDER                  (주문·견적 최종금액 계열)
  └─> TBL_CONTROL_PART           (소재비·가공비 등 원가 구성요소)
         └─ TBL_CONTROL_PART_ORDER / TBL_ORDER와 결합해 수주 단가검토
```

따라서 견적 단계 신규 컬럼은 장차 수주 단가검토에도 같은 의미로 사용할지, 주문 전환 시 어느 테이블로 복사할지를 함께 결정해야 한다.

## 3. 먼저 확정해야 할 데이터 귀속 단위

### 상세 행 단위

현재 상세 견적검토 팝업은 `EST_SEQ + SEQ`의 상세 행을 하나씩 저장한다. 각 도면·품목마다 배송비와 기타추가가 다르다면 `TBL_ESTIMATE_DETAIL` 귀속이 맞다.

### 견적서 전체 단위

배송비가 여러 상세 행을 묶은 견적서 전체에 한 번만 부과된다면 `TBL_ESTIMATE` 마스터 귀속이 맞다. 상세 행마다 같은 배송비를 저장하면 견적 합계에서 중복 가산될 수 있다.

### 권장 전제

현재 화면이 상세 행 단위이고 네 계산값도 상세 행 수량 `Q`를 사용하므로, 본 문서의 기본 권장안은 **상세 행 단위**다. 업무적으로 견적서 전체 배송비가 필요하면 별도의 마스터 배송비 정책을 추가해야 한다.

## 4. 대안 비교

## 대안 A — `TBL_ESTIMATE_DETAIL`에 명시적 컬럼 추가

### 제안 컬럼

| 컬럼 | 의미 | NULL 정책 | 비고 |
|---|---|---|---|
| `DELIVERY_AMT` | 상세 행 배송비 `D` | `NOT NULL DEFAULT 0` | 수량을 곱하지 않음 |
| `ADDITIONAL_AMT` | 신규 기타추가 `A` | `NOT NULL DEFAULT 0` | 기존 `UNIT_ETC_AMT`와 구분 |
| `APPLIED_TOTAL_AMT` | 사용자가 확정한 적용 금액계 `M` | `NULL` 허용 | NULL이면 계산값 사용 |

실제 금액 타입은 운영 DB의 기존 금액 컬럼 타입과 맞춰야 한다. 저장소 리포트는 기존 금액을 Java `Integer`로 다루지만 DDL 원본이 저장소에 없으므로, 적용 전 `SHOW COLUMNS`로 `UNIT_ETC_AMT`와 `UNIT_FINAL_EST_AMT`의 실제 타입·unsigned 여부를 확인해야 한다. 신규 구축이라면 일반적으로 `DECIMAL(18,0)`이 안전하다.

### 유효값 계산

```text
BASE_UNIT_AMT        = 기존 단가 구성요소 합(B)
UNIT_TOTAL_AMT       = B + DELIVERY_AMT + ADDITIONAL_AMT
QUANTITY_APPLIED_AMT = B × Q
CALCULATED_TOTAL_AMT = B × Q + DELIVERY_AMT + ADDITIONAL_AMT
EFFECTIVE_TOTAL_AMT  = COALESCE(APPLIED_TOTAL_AMT, CALCULATED_TOTAL_AMT)
```

`APPLIED_TOTAL_AMT`를 nullable하게 두는 이유는 `0`과 “사용자가 수정하지 않음”을 구분하기 위해서다.

### 장점

- 현재 화면·조회·저장 키(`EST_SEQ + SEQ`)와 정확히 일치한다.
- 조인 없이 읽고 저장할 수 있어 구현과 운영이 단순하다.
- 기존 `UNIT_ETC_AMT` 의미와 과거 데이터를 보존한다.
- 견적 버전 복사, 행 복사, 엑셀·리포트 적용 지점을 명시적으로 추적할 수 있다.
- 계산용 파생값을 중복 저장하지 않아 값 불일치 위험이 낮다.

### 단점

- 핵심 상세 테이블에 컬럼 3개가 늘어난다.
- 견적 생성·복사·버전 생성·수주 전환 SQL을 모두 갱신해야 한다.
- 적용 금액계를 수동 수정한 뒤 수량이나 가산액이 바뀔 때 override 유지/초기화 정책이 필요하다.
- 배송비가 실제로 견적 전체 단위라면 상세 행 저장이 잘못된 모델이 된다.

### 적합한 경우

- 배송비·기타추가·적용 금액계가 도면/품목 상세 행별 값이다.
- 추가금액 종류가 당분간 배송비와 기타추가 두 가지로 고정된다.
- 기존 시스템의 단순한 MyBatis 조회·저장 방식을 유지해야 한다.

## 대안 B — `TBL_ESTIMATE_DETAIL_AMOUNT` 1:1 확장 테이블

### 예시 구조

```sql
TBL_ESTIMATE_DETAIL_AMOUNT
  EST_SEQ            -- PK/FK 1
  SEQ                -- PK/FK 2
  DELIVERY_AMT
  ADDITIONAL_AMT
  APPLIED_TOTAL_AMT  -- NULL = 자동 계산
  INSERT_DT / INSERT_SEQ / UPDATE_DT / UPDATE_SEQ
```

### 장점

- 기존 핵심 테이블을 직접 확장하지 않아 스키마 변경 영향이 격리된다.
- 기능을 사용하지 않는 기존 견적에는 행이 없어도 된다.
- 신규 금액 기능의 감사 컬럼과 변경 이력을 독립적으로 관리하기 쉽다.
- 기능 롤백 시 기존 상세 테이블과 기존 계산을 건드리지 않는다.

### 단점

- 모든 상세 조회에 `LEFT JOIN`이 추가된다.
- 견적 버전 복사·행 복사·삭제 시 확장 테이블 동기화가 필요하다.
- 저장 순서와 트랜잭션 처리, 고아행 방지를 추가로 설계해야 한다.
- 단 3개 필드를 위해 1:1 테이블을 만드는 것은 현재 규모에서는 구조가 무거울 수 있다.
- 수주 전환 시에도 결국 주문 측 저장 위치가 별도로 필요하다.

### 적합한 경우

- 핵심 테이블 ALTER에 대한 조직적 제약이 크다.
- 신규 기능을 선택적으로 배포하거나 독립적으로 감사해야 한다.
- 향후 상세 금액 정책 필드가 더 늘어날 가능성이 높다.

## 대안 C — 가산항목 1:N 테이블 + 최종금액 테이블

### 예시 구조

```sql
TBL_ESTIMATE_DETAIL_CHARGE
  EST_SEQ, SEQ, CHARGE_SEQ
  CHARGE_TYPE       -- DELIVERY, ADDITIONAL, 향후 PACKING 등
  CHARGE_AMT
  NOTE

TBL_ESTIMATE_DETAIL_PRICE
  EST_SEQ, SEQ
  APPLIED_TOTAL_AMT -- NULL = 자동 계산
```

### 장점

- 포장비·긴급비·출장비 등 가산항목이 늘어나도 컬럼 추가가 필요 없다.
- 항목별 메모·순서·사용 여부·이력 관리에 유리하다.
- 여러 기타추가 항목을 각각 보존하고 합산할 수 있다.
- 장기적으로 가격 구성의 설명 가능성과 감사성이 가장 좋다.

### 단점

- 현재 고정 입력 2개만 필요한 화면에는 과도한 설계다.
- 조회 시 합계·pivot 또는 다중 행 처리 로직이 필요하다.
- 기존 엑셀·리포트·목록 쿼리의 변경 폭이 가장 크다.
- 중복 `CHARGE_TYPE`, 삭제, 정렬, 동시 수정에 대한 제약과 서비스 로직이 필요하다.
- 견적→주문 복사 규칙이 복잡해진다.

### 적합한 경우

- 신규 가산항목이 지속해서 추가될 로드맵이 확정돼 있다.
- 항목별 이력·사유·여러 건 입력이 실제 요구사항이다.
- 단기 구현비용보다 장기 확장성을 우선한다.

## 대안 D — `TBL_ESTIMATE` 마스터에 견적 전체 금액으로 저장

### 예시 컬럼

- `DELIVERY_AMT`
- `ADDITIONAL_AMT`
- `APPLIED_TOTAL_AMT`

### 장점

- 한 견적서에 배송비를 정확히 한 번만 가산할 수 있다.
- 견적서 총액·출력물 계산이 단순하다.
- 여러 상세 행에 같은 값을 중복 저장하지 않는다.

### 단점

- 현재 상세 행 팝업의 `B × Q` 계산과 귀속 단위가 맞지 않는다.
- 행별 금액계와 전체 견적 금액계의 의미가 섞인다.
- 상세 행마다 배송비나 기타추가가 다른 경우 표현할 수 없다.
- “저장/다음”으로 행별 편집하는 현재 UX와 충돌한다.

### 적합한 경우

- 업무 규칙상 배송비·기타추가는 무조건 견적서 전체에 한 번만 적용된다.
- 적용 금액계도 상세 행이 아니라 견적 전체 확정금액이다.

## 대안 E — 기존 컬럼 재사용 또는 계산 결과 전부 저장

예: `UNIT_ETC_AMT`를 신규 기타추가로 변경하거나, 단가합계·금액계·수량 적용가를 모두 컬럼으로 저장하는 방식이다.

### 장점

- 겉보기에는 신규 컬럼 수나 화면 계산 코드가 줄어든다.

### 단점

- `UNIT_ETC_AMT`의 216개 기존 참조와 과거 데이터 의미가 깨진다.
- 기존 쿼리 대부분이 기타추가에 수량을 곱하는 오류를 만든다.
- 파생값을 모두 저장하면 수량·단가·배송비 변경 시 네 금액이 서로 불일치할 수 있다.
- 어떤 값이 원본이고 어떤 값이 결과인지 불명확해진다.
- 회귀 범위가 매우 넓고 데이터 마이그레이션도 모호하다.

### 평가

권장하지 않는다.

## 5. 권장안

### 1순위: 대안 A

상세 행 단위라는 전제에서 `TBL_ESTIMATE_DETAIL`에 다음 3개만 추가하는 것이 현재 코드 구조와 가장 잘 맞는다.

```text
DELIVERY_AMT       -- 배송비, 수량 비례 아님, 기본 0
ADDITIONAL_AMT     -- 신규 기타추가, 수량 비례 아님, 기본 0
APPLIED_TOTAL_AMT  -- 사용자 override 총액, NULL이면 자동 계산
```

기존 `UNIT_ETC_AMT`는 기존 단가 `B` 구성요소로 그대로 보존한다.

### 2순위: 대안 B

조직 정책상 `TBL_ESTIMATE_DETAIL` ALTER가 어렵거나 신규 가격 정책을 별도 소유·감사해야 한다면 1:1 확장 테이블을 선택한다.

### 조건부 선택: 대안 D

배송비와 기타추가가 상세 행이 아니라 견적 전체에 한 번만 붙는다는 업무 결정이 내려지면 마스터 저장으로 전환한다. 이 경우 현재 화면의 네 계산식과 합계 표시도 견적 전체 관점으로 다시 정의해야 한다.

## 6. 적용 금액계 수정 정책 권장

사용자 수정 가능 필드는 다음 규칙이 안전하다.

1. 최초 조회: `APPLIED_TOTAL_AMT IS NULL`이면 계산값 `B × Q + D + A` 표시
2. 사용자가 적용 금액계를 직접 수정: 입력값을 `APPLIED_TOTAL_AMT`에 저장
3. 배송비·기타추가·수량·기존 단가 변경:
   - 권장: 기존 override가 있으면 “적용 금액계가 수동값입니다” 표시 후 유지
   - 별도 “자동계산값 적용” 버튼으로 `APPLIED_TOTAL_AMT = NULL` 복귀
4. 사용자가 0원을 명시하면 `0` 저장. NULL과 구분

금액 변경 때 override를 자동으로 덮어쓰면 사용자가 확정한 가격이 사라질 수 있으므로 권장하지 않는다.

## 7. 견적→수주 전환 시 권장 귀속

수주 단가검토는 원가 구성요소를 `TBL_CONTROL_PART`에서, 최종 견적·공급단가를 주문 매핑과 `TBL_ORDER`에서 읽는다. 또한 하나의 작업지시 파트에 여러 주문이 매핑될 수 있다.

따라서 향후 수주 화면까지 확장할 때는 다음을 권장한다.

- 기존 원가 `B`: 현행대로 `TBL_CONTROL_PART`
- 주문별 배송비·기타추가·적용 견적 총액: `TBL_ORDER` 또는 주문별 매핑 테이블
- 견적→주문 전환 시 `TBL_ESTIMATE_DETAIL` 신규 3컬럼을 주문 측 대응 컬럼으로 복사
- 주문과 무관한 작업지시 공통값으로 확정된 경우에만 `TBL_CONTROL_PART`에 저장

신규 가산액을 무조건 `TBL_CONTROL_PART`에 넣으면 동일 파트에 연결된 여러 주문의 가격 정책을 분리하지 못할 수 있다.

## 8. 구현 영향 범위

대안 A 적용 시 최소 확인 대상은 다음과 같다.

### DB

- `TBL_ESTIMATE_DETAIL` 컬럼 추가
- 기본값·NULL·금액 범위 제약
- 견적 버전 복사 및 상세 복사 SQL
- 필요하면 주문 측 대응 컬럼과 변환 SQL

### 조회·저장

- `v1/estmateCalculate.xml`: 신규 3컬럼 조회
- `estmateCalculate.xml`: 신규 3컬럼 저장
- `estimate.xml`: 생성·수정·버전 복사·주문 전환
- 견적 목록/등록 쿼리: 표시 및 합계식 변경
- 엑셀·리포트: 합계 정의 변경 여부 확인

### 화면

- 현재 임시 `UNIT_DELIVERY_AMT`를 DB명 `DELIVERY_AMT`로 통일
- 현재 `기타추가`에 잘못 연결된 `UNIT_ETC_AMT`를 `ADDITIONAL_AMT`로 분리
- 숨겨진 중복 `UNIT_ETC_AMT` DOM 제거 또는 기존 기타비용 용도 명확화
- 계산 배열을 `기존 단가 항목`과 `행 가산액`으로 분리
- 수량 적용가·적용 금액계 셀에 ID와 입력 제어 추가
- 수동 override 상태 표시와 자동계산 복귀 동작 추가

### 회귀 검증

- 기존 데이터에서 신규 컬럼 0/NULL일 때 계산 결과가 변경되지 않는지
- 배송비·기타추가에 수량이 곱해지지 않는지
- 수량 0·1·다수 케이스
- 적용 금액계 수동 수정 후 저장·재조회
- 수동값 0과 미수정 NULL 구분
- 저장/다음 행 전환 및 빠른 행 전환
- 견적 버전 복사 및 견적→주문 전환
- 견적목록·엑셀·Jasper 출력 합계

## 결론

현재 요구에는 기존 컬럼 재사용보다 **기존 의미를 보존한 명시적 신규 컬럼**이 안전하다. 상세 행 단위가 맞다면 `TBL_ESTIMATE_DETAIL`에 `DELIVERY_AMT`, `ADDITIONAL_AMT`, `APPLIED_TOTAL_AMT`를 추가하는 대안 A를 권장한다. 파생값인 단가합계·금액계·수량 적용가는 저장하지 않고 계산하며, 사용자 override만 nullable 컬럼으로 보존한다.

다만 배송비가 견적 전체에 한 번만 부과되는 값이면 테이블 귀속이 달라지므로, DDL 승인 전 귀속 단위부터 확정해야 한다.
