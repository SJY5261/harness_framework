# Architecture Decision Records: Tomes-Cloud

## 철학
안정적인 운영 우선. 검증된 기술 스택을 유지하고,
변경은 최소 범위로 점진적으로 적용한다.

---

### ADR-001: MyBatis 선택 (JPA 미사용)
**결정**: ORM으로 JPA 대신 MyBatis XML 매퍼 사용
**이유**: 복잡한 ERP 쿼리(다중 조인, 동적 SQL, 집계)가 많아 SQL을 직접 제어해야 함
**트레이드오프**: SQL을 직접 작성해야 하지만 쿼리 최적화와 디버깅이 용이

### ADR-002: JSP + Apache Tiles (모던 프론트엔드 미사용)
**결정**: React/Vue 대신 JSP + JSTL + Apache Tiles 유지
**이유**: 기존 레거시 구조 유지로 안정성 확보, 전면 교체 비용 최소화
**트레이드오프**: 프론트엔드 개발 생산성은 낮지만 운영 안정성 우선

### ADR-003: ParamQuery Grid 11.0.0
**결정**: UI 그리드 라이브러리로 ParamQuery Grid 사용 (7.x → 11.0.0 마이그레이션 진행 중)
**이유**: 대용량 데이터 테이블, 인라인 편집, 다양한 에디터 지원이 ERP에 적합
**트레이드오프**: 버전 간 API 변경으로 마이그레이션 비용 발생

### ADR-004: Redis 세션·캐시
**결정**: 세션 관리와 캐시를 Redis로 처리 (Spring Session + Spring Cache)
**이유**: 서버 재시작 시 세션 유지, 향후 멀티 인스턴스 확장 고려
**트레이드오프**: Redis 인프라 의존성 추가

### ADR-005: 이중 인증 (JWT + 파일 토큰)
**결정**: JWT와 파일 토큰 두 가지 인증 방식 병행
**이유**: (추론) 웹 브라우저는 JWT, 외부 시스템·배치 연동은 파일 토큰으로 분리한 것으로 추정
**트레이드오프**: 인증 경로가 두 개로 관리 복잡도 증가

### ADR-006: WAR 배포
**결정**: 실행 가능한 JAR 대신 WAR 파일로 Tomcat에 배포
**이유**: 기존 서버 환경(Tomcat + Nginx reverse proxy) 유지
**트레이드오프**: 배포 절차가 JAR보다 복잡하지만 기존 인프라 재사용

### ADR-007: 멀티테넌트 — 서브도메인 기반
**결정**: 도입 기업별로 `dev-{SYSTEM_ID}.tomes.kr` 서브도메인 부여
**이유**: 단일 서버에서 기업별 데이터 분리, 기준코드 공통화로 운영 효율화
**트레이드오프**: 신규 고객사 추가 시 도메인·기준코드 설정 작업 필요

### ADR-008: 테넌트 정책 — 테넌트 우선·공통값 후퇴
**결정**: 현재 클라우드에서 `BASIC`과 `USE_YN`으로 공통 정책을 운영하더라도, 테넌트 민감 기능은 실제 `SYSTEM_ID`의 정책을 우선 해석하고 없을 때 공통값으로 후퇴할 수 있게 설계한다.
**이유**: 클라우드는 회사 공통 규격 중심이지만 향후 인수할 수 있는 온프라미스는 고객별 요구 중심이므로, 현재 기능부터 양쪽에서 활용할 수 있는 범용 코드로 만들고 온프라미스에는 그대로 가져가거나 최소한의 정책 확장만으로 적용하기 위함이다.
**트레이드오프**: 현재 클라우드만 보면 정책 조회 경계가 하나 늘지만, `BASIC` 하드코딩 확산을 막고 향후 온프라미스 적용 비용을 줄인다. 다만 확인되지 않은 고객별 세부 요구까지 추측해 관리 UI나 배포 구조를 미리 만들지는 않는다.
