여섯 가지 핵심 원칙

이 여섯 항목만 기억해도 대부분의 잘못된 테스트 실행과 허위 통과를 막을 수 있다.

01

결과를 확인한다

버튼 클릭, 주소 이동, 팝업 테두리만으로 통과시키지 않는다. 화면·목록·파일·DB 결과를 확인한다.

02

바꾼 것은 되돌린다

변경 전 값을 기록하고, 실행 후 원상복구한 다음 다시 조회해 복구 여부를 확인한다.

03

검사를 약하게 만들지 않는다

실패를 없애기 위해 기대값이나 확인 조건을 삭제하지 않는다. 실패는 원인을 찾으라는 신호다.

04

정해진 절차부터 쓴다

저장된 테스트 순서와 공통 실행 절차를 먼저 사용한다. 인공지능은 명시적으로 허용된 마지막 단계다.

05

사람이 만든 테스트를 보호한다

사람이 직접 확정한 테스트 순서는 자동으로 덮어쓰지 않는다. 실패 시 별도 분석 대상으로 남긴다.

06

작게 실행하고 즉시 멈춘다

1→5→10→20건으로 확대한다. 실패나 추가 분석 신호가 나오면 원인을 해결하기 전까지 범위를 늘리지 않는다.

어떤 규칙을 먼저 따르나

아래쪽 문서가 위쪽 규칙과 충돌하면 위쪽을 따른다. 과거 기록의 상태값은 다시 측정한다.

통과 판정 흐름

테스트가 끝났다는 것과 통과했다는 것은 다르다. 아래 순서를 모두 지나야 통과로 기록할 수 있다.

STEP 01

요청 범위 확인

어떤 화면과 기능을 확인하는지, 외부 기록이나 데이터 변경이 있는지 먼저 정한다.

STEP 02

정해진 절차 실행

저장된 테스트 순서와 공통 실행 절차를 사용해 작은 범위부터 실행한다.

STEP 03

실제 결과 확인

화면 상태, 목록 데이터, 다운로드 파일 또는 DB 값으로 사용자 효과를 확인한다.

STEP 04

변경 내용 원복

저장·수정·삭제가 있었다면 원래 상태로 되돌리고 재조회한다.

STEP 05

증거와 함께 기록

사용한 절차와 확인한 증거, 원복 결과를 설명에 포함해 통과 또는 실패를 기록한다.

기능별 통과 기준

행동을 했는지가 아니라 행동의 결과가 실제로 발생했는지를 기준으로 판정한다.

⌕

검색·필터

검색값이 입력됐고 목록 또는 입력 영역이 그 조건에 맞게 바뀌어야 한다.

▣

팝업

올바른 팝업이 열리고 주요 값·목록·버튼이 사용할 수 있는 상태여야 한다.

⇩

다운로드

실제 파일이 다운로드되거나 지정된 증적 폴더에 저장돼야 한다.

↺

저장·수정·삭제

변경 결과와 원상복구 결과를 화면 또는 DB에서 모두 확인해야 한다.

통과가 아닌 예: 버튼만 클릭함 · 팝업 테두리만 확인함 · 다운로드 주소만 확인함 · 가짜 선택지를 만든 뒤 성공함 · 단순히 참 값을 반환하는 코드만 실행함

테스트 절차 작성 규칙

테스트 순서에는 무엇을 검증할지 적고, 실제 조작은 재사용 가능한 작은 절차로 나눈다.

권장하는 방식

  • 이미 있는 공통 실행 절차를 먼저 찾는다.
  • 화면 진입·검색·팝업 열기·본문 확인을 분리한다.
  • 하나의 실행 절차는 한 가지 목적에 집중한다.
  • 공통 팝업은 주요 필드와 버튼 구조로 구분한다.
  • 기능 변경 시 기존 업무 조건을 새 검사에도 유지한다.

피해야 하는 방식

  • 긴 자바스크립트 전체를 테스트 순서마다 복사한다.
  • 실패하는 조건을 삭제해 테스트만 통과시킨다.
  • 화면에 없는 선택지나 데이터를 임의로 생성한다.
  • 사람이 직접 확정한 테스트를 자동으로 덮어쓴다.
  • 실제 결과 없이 클릭 성공만 통과로 기록한다.

TOMES 화면 조작 규칙

일반 웹사이트와 다른 jQuery·pqGrid·탭 화면의 특성을 고려한다.

로그인입력란 클릭 후 키보드 입력. 값을 한 번에 넣는 방식은 피한다.
대기통신 종료가 아니라 필요한 버튼·입력란·목록 데이터가 나타나는지를 기다린다.
메뉴상위 메뉴에 마우스를 올리고 클릭한 뒤 펼침 동작을 기다려 하위 메뉴로 이동한다.
새로고침메인으로 돌아갈 수 있으므로 같은 화면에 다시 진입한 뒤 값을 측정한다.
탭같은 식별자가 중복될 수 있어 현재 활성 탭 안에서만 요소를 찾는다.
고정 대기짧은 초기화 보조용으로만 쓰고, 상태 확인을 대신하게 하지 않는다.
계정주소와 계정은 환경 설정 파일에서 읽고 코드나 문서에 직접 적지 않는다.
실패 대응위치·타이밍·활성 탭·테스트 데이터·브라우저 상태 순으로 원인을 확인한다.

데이터와 외부 기록 안전

되돌릴 수 없는 변경은 테스트 성공보다 위험하다. 실행 전에 복구 방법부터 확보한다.

DB 변경 전 정할 것

  • 변경할 테이블과 대상 행의 고유 식별값
  • 변경 전 값 또는 전체 백업 행
  • 테스트로 생성할 데이터의 이름 범위
  • 성공·실패와 관계없이 실행할 원상복구 방법
  • 복구 후 정상 여부를 확인할 재조회 방법

구글 시트 기록

  • 실제 통과·실패·오류만 결과와 날짜를 갱신한다.
  • 추가 분석·사람 확인·사용자 결정은 설명만 기록한다.
  • 자동화 실패로 기존 수동 통과 결과를 실패로 바꾸지 않는다.
  • 통과 설명에 확인 증거와 원상복구 결과를 남긴다.
  • 시트 기록 옵션은 외부 상태 변경임을 인식한다.
